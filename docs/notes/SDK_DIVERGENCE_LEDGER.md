## How to decide

Each row is one rule on which the generic app (frontend) and the MCP server interpret the metadata contract differently, or a frontend quirk the golden outputs captured. Attribution is exact: a difference is counted for a row only when both golden values equal the reference models of the cited code and the row's transformation turns one into the other; any other difference fails the ledger run, so the rows account for every computed divergence. `scripts/golden/ledger-mutation-check.sh` proves this by mutating the MCP and the frontend code and requiring the run to fail.

Counting: an instance is one distinct example / entity / subject (property, view entry, condition and record, payload, query case and aspect, action); `occurrences` counts it once per role variant. `synthetic` instances come from fixed input sets (the `_shared` matrices, payload sets and type probes) rather than from example metadata. `effects` are downstream differences a rule causes elsewhere (a select string that differs because the type differs). `harness-only` instances arise only from the golden harness's inputs, not from the real app. Rows with 0 instances in examples are latent: the evidence is the cited code plus synthetic inputs. The `.es` variants are excluded: the MCP never receives translated metadata (N-05).

Daniel decides per row at gate 2. Recommendations:

- `adopt-frontend`: the core implements the frontend behavior; the MCP output changes (an approved golden diff in P1.3).
- `adopt-mcp`: the MCP rule is strictly better; the core implements it and the frontend output changes as an approved golden diff in P1.3.
- `mcp-bug` / `frontend-bug`: the side named is wrong; fix it there (the core gets the correct behavior).
- `needs-decision`: a real trade-off; the row states the options.

Record the decision in the `decision` field of `tests/golden/ledger.json` (or tell the lead); P1.3 turns every `adopt-mcp` decision and every fixed bug into an entry in `tests/golden/approved-diffs/`. Tie-order differences between the two trees are capture artifacts, not rows (see Coverage).

## Type detection

`SchemaService.getPropertyType` (frontend) vs `detectPropertyType` (MCP). Artifacts: `<variant>/schema.properties.json` `type` on both sides; latent rules are demonstrated by `mcp/_shared/mcp.type-probes.json`. Every probe is compared: its frontend type comes from the transcription of `getPropertyType` in `scripts/golden/ledger-models.mjs` (`feType`), which is checked against the frontend type of every fixture property and of every row of the hand-built frontend `_synthetic` golden variant (which reaches every frontend result type, DateTime and RecurringTimeSlot included); branches neither exercises are anchored by that transcription only. The Coverage section lists them, computed: on the MCP side DateTime and RecurringTimeSlot (until P0.5 adds a real timestamp column), and udt values in no raw fixture such as int2, bpchar, float4 / float8, jsonb, MultiPolygon. Follow-up: run the probe inputs through the frontend golden harness.
